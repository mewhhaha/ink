# 2D: sprites, tile maps, text and an editor for them

The same session, hot reload, hand-offs and tools work for 2D games. A 2D game
is a schema with `standard.components2d`, Blot code, a scene and some atlases;
`examples/tiles` (`deno task dev:tiles`) is a tile editor and a small platformer
built from them, and `docs/blot.md` covers the `ink/tiles` library.

## Components

```ts
defineSchema({
  components: {
    transform: standard.transform,
    camera: standard.camera, // orthographic: true, size: 11.25
    sprite: standard.sprite,
    tilemap: standard.tilemap,
    light2d: standard.light2d,
    text: standard.text,
  },
});
```

| Component | What it is                                                                                                                                                     |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sprite`  | An atlas frame (or a plain `texture`) with tint, flips, pivot, `pixels_per_unit`, `layer`, `y_sort`, `lit`, `smooth`, `snap`, and an animation id plus time.   |
| `tilemap` | `width` x `height` tile ids in `cells`, the `tileset` atlas, `cell` size in world units, `layer`, `lit`, and `occluder` (solid tiles cast light shadows).      |
| `light2d` | `lamp`, `spotlight`, `sun` or `ambient`, with colour, intensity, radius, falloff, height above the plane, cone angle and `shadows`.                            |
| `text`    | A schema message (or, with message 0, the entity's name) with two numbers filling `{0}` and `{1}`; size, colour, alignment and outline. Distance field glyphs. |

Everything lives on the entity's transform plane, so the usual hierarchy works:
a HUD is `text` entities that are children of the camera.

Animation follows the rest of Ink: `sprite.anim` and `sprite.anim_time` are
ordinary state the game advances, so rewind and hand-offs reproduce the frame.

## Atlas files

`assets/hero.atlas.json` names the parts of an image:

```json
{
  "ink": 1,
  "image": "hero.png",
  "normals": "hero_n.png",
  "grid": { "cell": [16, 16], "columns": 8, "rows": 3 },
  "names": { "idle_0": 0, "idle_1": 1 },
  "frames": { "big_door": [0, 64, 32, 48] },
  "animations": { "idle": { "frames": ["idle_0", "idle_1"], "fps": 2 } },
  "tiles": { "ground_15": ["solid"], "plank": ["oneway"] },
  "autotile": {
    "ground": { "tiles": ["ground_0", "...16 names, by neighbour mask"] }
  }
}
```

Frame ids are 1-based: the grid cells row by row, then the free rectangles. Tile
flags are `solid`, `oneway`, `ladder` and `hazard`. Auto-tile rules list 16
tiles indexed by which neighbours (N=1, E=2, S=4, W=8) are part of the group;
the editor's brush picks the variant itself.

Blot refers to all of it by generated constants, named like the other assets:

```blot
s.atlas_hero              // the asset id, for sprite.atlas
s.frame_hero_idle_0       // frame ids; in a tile map they are tile ids
s.anim_hero_idle          // animation ids, for sprite.anim
s.tileflags_hero          // Array U32 of flags by tile id, for ink/tiles
```

Editing an atlas file regenerates those constants, rebuilds the game and
refreshes the editor's palette while the game plays; a file that is mid-edit and
does not parse keeps the last good version (the dev server logs why). Replacing
the image file reloads the texture in place.

## Where the tile data lives

A tile map's ids are an ordinary `list(u32)` component field (`cells`, at most
32,768, so up to 128 x 256), not an asset file. That is the point of the design:
tile edits are session edits, so they are undoable, recorded by the timeline,
included in hand-offs and scenario states, merged by shared editing, visible to
comments, and they change the _playing_ world: Blot reads the same cells for
collision, so painting a wall during play stops the hero at once. The cost is
that a step packet carries the map: one F32 lane per cell, 8 KB for a 2,048 cell
level, about 130 KB for the largest map. The runtime copies the world each step
today, so a 64 x 32 level costs microseconds; maps of tens of thousands of cells
are where the transport shows up in a profile. Prefer several smaller maps
(layers, rooms) to one huge one. A runtime that keeps the world in the guest and
sends only changed entities shrinks the cost without changing this format.

Scene files stay readable: long runs of numbers wrap like prose, one row of
`cells` per ~100 columns, so a diff of a level is a diff of a few lines.

A bigger design is possible without changing the components: store only the
edits to a base map asset (`cells` as an override list). It was not chosen
because Blot collision needs the base data in the world, and a map that exists
in two places has to be reconciled by every tool.

## Editing

`@ink/tiles` is to tile maps what `@ink/brushes` is to brushes:

```tsx
const tools = createTileTools();
<InkApp tools={tools}>
  <TopBar>
    <ToolPicker tools={tools} />
  </TopBar>
  <Viewport
    id="level"
    view="front"
    tools={tools}
    shading="lit"
    overlay={pixelGrid}
  />
  <Panel title="Tiles">
    <TilePalette />
  </Panel>
  <Panel title="Layers">
    <TileLayers />
  </Panel>
</InkApp>;
```

Tools: paint (B; Shift draws lines, Alt picks), erase (E), rectangle (R; Shift
is the outline), flood fill (G) and tile picker (I). Each stroke is one undoable
transaction, auto-tiles the cells it touches and their neighbours, and works
while the game runs. `TilePalette` is a tileset browser read from the catalog,
`TileLayers` lists the tile map entities (hide, choose, add, resize),
`pixelGridLines` draws the texel grid once it is big enough to see. The edit
functions in `@ink/tiles` (`paint`, `fillCells`, `rectCells`, `retile`, ...) are
pure, for scripts and tests.

The Viewport takes `frameOnOpen` (frame the scene, or choose a view) and
`hideEntity` (keep a game's HUD out of the level view) for 2D editors; the
`ui.hidden` list hides entities in every view while editing.

## Rendering and what to know

See the renderer README for the details: a display-referred layer in the overlay
pass (no tonemapping, TAA or render scale applied to it), nearest sampling, one
draw per tile map, normal-mapped lights, tile shadows, distance field text.
Shipping players draw it the same way.

## The example

`examples/tiles` ships original procedurally drawn art (`scripts/art.ts` writes
the PNGs, normal maps and atlas files), a starter level and a blank map
(`scripts/level.ts`), a platformer in Blot (run and jump with coyote time and a
jump buffer, ladders, one-way planks, slimes to stomp, coins, spikes, a flag,
HUD text) and its editor: tools, tileset palette, layers, an objects palette to
place the hero, coins, slimes, torches and the flag, the level and game views
side by side, timeline, comments, hand-offs and a recorded playthrough with
golden images (`deno task ink test examples/tiles`).

`deno task test:tiles` builds a level on the blank map with the real tools (a
floor, a pit with spikes, planks, crates, a fill, an eyedropper, objects), saves
it, plays it with a bot and wins, then edits Blot code, the tileset image, the
atlas file, tiles and the editor's own source while the game is playing, and
checks a capture, a hand-off with its replay and the recorded scenario.
